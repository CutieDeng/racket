# Hand-tuned assembly for rktcrypto (AArch64)

Performance-critical inner kernels written in **rktasm** (formerly *asmp*) —
an ARM64 assembler (S-expression / annotated-GNU syntax with virtual
registers, graph-colouring register allocation, and ABI-aware
prologue/epilogue) now in-tree at `racket/src/rktasm` (override with the
`RKTASM` env var). Older docs/provenance headers refer to it as "asmp".

## Build-time independence

The asmp tool is a **development-time** dependency only. Each kernel is
committed in two forms:

- `asm/<name>.asm` — the asmp source (edited / generated by hand).
- `rktcrypto_<...>.S` — the assembler output, wrapped in a preprocessor
  guard, **committed and compiled directly by the normal build**
  (`build.zuo`). The build never invokes asmp or Racket.

So a fresh checkout builds with only a C toolchain; asmp is needed only to
*regenerate* a `.S` after changing a `.asm`.

## Kernels

The table is authoritative against `asm/regen.sh`'s TABLE (the `source → .S`
mapping is machine-checked by `regen.sh check`). **source kind**: *gen* = a
generator emits the `.asm` — Racket emitters under `asm/gen/` that `require`
asmp's `parser/gnu-writer.rkt` (construct AST, deterministic serialization,
reparse self-check; all five legacy `.py` text generators were migrated in
Phase F, see `../ASM-ENHANCEMENT-PLAN.md`); *hand-.asm* = a hand-scheduled
`.asm` with named virtual registers
(no live generator, the `.asm` IS the source of truth); *.context* = a
hand-.asm that additionally declares a cross-function shared register-ABI via
`.context` (§ below); *hand-.S* = a hand-written `.S` with no asmp source
(honest orphan).

`asm/gen/` layout: `gw.rkt` locates the in-tree rktasm (`RKTASM` env var, same
convention as `regen.sh`) and re-exports `gnu-writer`; one emitter module per
kernel family (`mulplain.rkt` = `emit-mul-plain K`, replacing the two-variant
`gen_mulplain.py`); `asm-equiv.rkt` compares two `.asm` files at the AST level
(the migration instrument: proves a new emitter's output semantically equal to
the retired generator's committed `.asm`, layout-independent).

*known-drift* = the committed `.S` predates the current asmp allocator, so
`regen.sh check` reports a benign register-numbering drift (whitelisted; a
re-commit must first pass the differential gate). *bn_sqr* is the sole honest
orphan (its frame-pointer + runtime-sized stack frame is beyond what `.save all`
can own; see `../ASM-ENHANCEMENT-PLAN.md` A5).

Three `.asm` sources concatenate into `rktcrypto_p256_asm.S`
(`mont_mul`/`mont_mul_p256`/`mont_sqrn`); `asm/regen.sh` handles it. The
OpenSSL-parity point-double `_jac_double_hw`, mixed-add `_mixed_add_hw`, their
field helpers (`_p256_mul/_sqr/_add/_sub_from/_sub_morf/_div2`) and the
dedicated mod-p squarer `_mont_sqrn_p256` live in `rktcrypto_p256_hand.S`,
regenerated from `asm/p256_hand.asm`: a single `.context p256_field
(scope library)` declares their shared OpenSSL-internal register-ABI once
(operands x4-x7/x8-x11, results x14-x17) instead of hardcoding it per kernel,
and `.save all` generates the callee-saved frame for the two point ops — the
hand instruction schedule is preserved bit-for-bit (see that file's header and
the § on `.context` below). `rktcrypto_p256.c`'s `mont_mul` dispatch picks by
ctx:

- `mont_mul_p256(r,a,b)` — **field prime p** (all point arithmetic).
  Interleaved CIOS (OpenSSL ecp_nistz256-armv8 structure): 4 iterations of
  {multiply-accumulate one word of b, then reduce}, keeping the accumulator
  at 6 words. Because n0 = 1 for p and p has Solinas limbs, each reduction is
  9 instructions (lsl/lsr + subs/sbc + 5 adds) — no reduction multiply.
  ~147 instructions vs an SOS full-product's ~235; **170 Mmul/s throughput
  (independent muls) vs SOS 97**, the number point arithmetic actually hits.
  Squaring routes here too (mont_mul_p256(a,a) = 150 Msq/s, beats a separate
  SOS symmetric squarer).
- `mont_mul_asm(r,a,b,ctx)` — **group order n** (scalar ops). Generic CIOS
  reading ctx->m/ctx->n0. Uses `.save all` so the ~19-live working set spills
  into callee-saved GPRs (x19-x26, saved once) instead of NEON (an `fmov`
  before every mul); 0 fmov, ~11.5 ns/op (n/p 1.58x). This is the mod-n
  multiply under ECDSA's `scn_inv` (Fermat inverse mod n) — the change lifted
  ECDSA sign ~+9%, verify ~+3%.

Key lesson (measured): on the wide OoO M1 core the field multiply is
*latency-bound* on the serial carry chain when muls are chained, but point
arithmetic runs *independent* muls, so **throughput** is what matters — and
the interleaved CIOS's lower instruction count wins there even though its
chained-latency is similar to SOS. The ctx pointer is a compile-time
constant at essentially every call, so the dispatch branch folds under
inlining.

## Regenerating a kernel

Use `asm/regen.sh` (Phase 0 tooling; see `../ASM-ENHANCEMENT-PLAN.md`):

```sh
asm/regen.sh check           # verify committed .asm/.S reproduce from sources
asm/regen.sh gate [kernel]   # regen with current asmp to a temp .S and run its
                             # differentials against THAT (working tree untouched)
asm/regen.sh regen <kernel>  # rewrite .asm + .S, then auto-gate what it wrote
asm/regen.sh list            # kernels and support status
```

`check` compares instruction bodies (comments/guards stripped), so the
`--keep-comments` semantic comments and provenance headers never affect it.
`bn_sqr` is the sole kernel without a committed asmp source (honest orphan,
`SKIP`; see table). `keccak` and `_mont_mul_p256` are known drifts (the asmp
allocator evolved since those `.S` were committed) — do not re-commit them
until the differential harness gates a regenerated version.

The manual flow (what regen.sh does under the hood):

```sh
RKTASM=../rktasm   # in-tree, relative to racket/src/crypto
# 1. (re)generate the asmp source IF it is script-produced (e.g. bn_op, sha1);
#    hand-.asm and .context kernels (mont_mul*, md5, p256_hand) skip this step.
RKTASM=$RKTASM racket asm/gen/opscan.rkt 16 asm/mont_mul_op16.asm
# 2. assemble to Apple AArch64 syntax (must run with cwd=$RKTASM for config/).
#    p256_hand additionally needs --allow-sp-writes (hand M3 scratch frames).
(cd $RKTASM && racket cli/as.rkt --gnu-input --apple --elim --default-abi aapcs64 \
    --keep-comments -o /tmp/body.s <abs-path>/asm/mont_mul_op16.asm)
# 3. wrap in the platform guard and commit as the .S
{ printf '#if defined(__aarch64__) && defined(__APPLE__)\n'; cat /tmp/body.s; \
  printf '\n#endif\n'; } > rktcrypto_bn_op.S
```

Add `--debug-reg-map` (allocation map) or `--dump=interference` (conflict
graph) when tuning register pressure.

## `.context` — cross-function shared register-ABI (one kernel: p256_hand)

A hand-scheduled kernel *family* that calls between its members and shares a
fixed register convention (operand in x4-x7, result in x14-x17, …) has an
**implicit register-ABI contract**. `p256_hand.asm` declares it *once* with

```
.context p256_field (scope library) a0=x4 … acc0=x14 … rp=x0 bp=x2
.function p256_mul (context p256_field)   ; body uses x.a0, x.acc0, …
```

The asmp `apply-contexts` pass substitutes `x.<field>` → the mapped physical
register before allocation (schedule unchanged), and the `scope library` L1
check errors at assemble time if an exported member uses a callee-saved context
field without `.save`. This replaced the former per-kernel hardcoded ABI +
hand `stp x19-x22` frames (ASM-ENHANCEMENT-PLAN.md audit risks ④/⑤, milestone A7).

**Do not spread `.context` by reflex.** It earns its DSL cost *only* at a
cross-function shared register-ABI. Single-function pseudo-names (e.g. md5) want
plain SSA renaming; asmp-allocated kernels want plain named virtuals;
frame-pointer / variable-alloca kernels (e.g. bn_sqr) do not fit it at all. Full
decision matrix: `../rktasm/docs/context-register-sets-design.md` §7.1. In this
tree the contract occurs exactly once — hence exactly one `.context` source.

## Per-kernel gates (Phase 0)

- `asm/tests/test_*.c` — per-kernel differential (≥200k random + edges,
  oracle = portable C) + ABI clobber sentinel + ns/op bench, one binary per
  kernel family; build lines in each file header and in `asm/BASELINE.md`.
  Covered families: `test_bn` (bn_op/fips/sqr), `test_md5_sha1`, `test_keccak`,
  `test_keccak_f2`, `test_reduce_p384`, `test_p256_extra` (mont_sqrn/jac_double),
  `test_mixed_add`, `test_mont_sqrn`, `test_ecc_mul`, and **`test_mont_mul`**
  (mont_mul_p256 mod p / mont_mul_asm mod n — the P-256 core Montgomery
  multiplies; added 2026-07-31 after an audit found they had only end-to-end
  coverage while `mont_mul_p256` is a regen known-drift).
- **`asm/regen.sh gate [kernel]`** — the re-gating is now **automated, not a
  discipline**: it regenerates the kernel from the committed `.asm` with the
  *current* asmp into a temp file (working tree untouched) and runs that
  family's differentials against **the regenerated `.S`**, exiting non-zero on
  any mismatch. `regen <kernel>` runs it automatically on what it just wrote and
  tells you to roll back if it fails. This is what makes a **known-drift** kernel
  (`keccak`, `mont_mul_p256`) safe to trust: `check` can only report their drift,
  never their correctness — only `gate` can. (Audited 2026-07-31, re-verified
  2026-08-02 via the automated gate: all 9 kernels PASS; fault-injection test
  confirms the gate catches a one-instruction semantic break, 199999/200000.)
- **Performance is gated too, and it is load-immune.** `gate`/`regen` follow the
  differential with an **interleaved A/B** of the regenerated `.S` against the
  committed one (same machine, same instant, median of 5 alternating rounds),
  failing on a **>2%** slowdown (`PERF_TOL` to override). Bodies identical →
  skipped, since perf is then unchanged by construction. This deliberately does
  *not* compare against BASELINE.md's absolute numbers: this box drifts ±15% with
  load, so absolute comparison manufactures false alarms — only a same-instant
  ratio answers "did this regen get slower". (Null control: the same `.S` in both
  A/B slots reads ±0.2%.)
  - This immediately paid for itself: the **`keccak` known-drift is not benign** —
    current asmp's allocation is **2–5% slower** across all five rates (same
    direction, well outside the ±0.2% control), which is *why* it stays
    whitelisted and must not be re-committed. `p256`'s drift is perf-neutral
    (±0.3%). Both are correctness-clean; only `gate` could tell them apart.
- `asm/BASELINE.md` — recorded performance baseline (kernel-level and
  end-to-end), for tracking absolute levels across machines/sessions. Treat it as
  a *reference*, not a gate: the enforced regression check is the A/B above.

## Verification discipline (mandatory)

Assembly is **never** committed without passing, against the portable C as
oracle:

1. **Bit-exact differential** over ≥200k random inputs incl. edge cases, for
   every modulus/parameterisation the kernel serves.
2. **ABI clobber guard** — callee-saved x19–x28 (and v8–v15) must survive a
   call (sentinel check).
3. End-to-end: the built binary passes `crypto-subsystem-self-test?`, the
   P-256 consistency sweep, and the OpenSSL differential.

The pilot harness lives under the scratchpad (`montmul_test.c`): oracle =
`mont_mul_portable`, subject = `mont_mul_asm`.

## Portability

`rktcrypto_p256_asm.S` is guarded `#if defined(__aarch64__) &&
defined(__APPLE__)` and matches the routing guard in `rktcrypto_p256.c`. On
every other target the object is empty and P-256 uses `mont_mul_portable`. A
GNU/ELF AArch64 variant (for aarch64-linux) is a straightforward follow-up:
emit with `--gnu` and widen the guard.
